# Episode 4: Attention efficiency, K V cache, M Q A, G Q A, Flash

Welcome to episode four. In episode one we talked about the quadratic cost of self-attention. Every position attends to every other position, so the cost scales as n squared with sequence length. For years, that was presented as the central efficiency problem of transformers. And it is real. But there is a different bottleneck that turned out to matter more in practice, especially at inference time. That bottleneck is memory, and specifically the key-value cache.

Today we are going to cover three things. First, why the K V cache exists and why it dominates inference cost. Second, multi-query attention and grouped-query attention, which shrink the cache. Third, flash attention, which does not change what attention computes but radically changes how it uses memory during training. Prior approach, what changed, why it won.

Let me start with why inference is a fundamentally different problem than training. During training, you process a batch of sequences, compute the loss on all of them in parallel, backpropagate, update the weights. The forward pass is fully parallel, as we covered in episode one. Every position in the sequence computes its query, key, and value simultaneously. You do the attention computation once, for the full sequence, and you are done. The main resource constraint during training is compute, measured in F L O Ps.

Inference is different in a crucial way. When a model generates text, it produces one token at a time. It generates token one, then uses that to generate token two, then uses tokens one and two to generate token three. This is called autoregressive decoding, and it is inherently sequential. Each step, the model runs a forward pass to produce the next token's probability distribution. And at each step, the attention layer needs to compute the dot product of the new token's query with the keys of every previous token.

Here is the naive approach. At step t, recompute the keys and values for all t tokens from scratch, then do the attention. This means at step one hundred, you are recomputing the keys and values for the first ninety-nine tokens, even though they have not changed since you computed them in earlier steps. At step one thousand, you recompute nine hundred and ninety-nine sets of keys and values you already have. This is absurdly wasteful. The compute cost per generated token grows linearly with the sequence length, and you are doing redundant work at every step.

The K V cache is the obvious fix. At each step, when you compute the key and value for the new token, you append them to a running cache. At step t, the cache contains the keys and values for tokens one through t minus one. You only compute the new token's query, key, and value. Then you dot-product the query against all cached keys, do the softmax, and average the cached values. One new set of key-value vectors computed per step, instead of recomputing all of them.

This is a massive speedup. It turns the per-step compute from being dominated by redundant key-value computation to a single vector-matrix product, one query against all cached keys. But it introduces a new problem. Memory.

Let me do the arithmetic on how big the K V cache gets, because the numbers are what make this real. For each token in the sequence, you store one key vector and one value vector, per layer, per attention head. Consider Llama two seventy billion. It has eighty layers, sixty-four attention heads per layer, with a head dimension of one hundred and twenty-eight. In sixteen-bit floating point, each element is two bytes. So each key vector is one hundred and twenty-eight times two, which is two hundred and fifty-six bytes. Same for each value vector. Per token, per head, per layer, you store two hundred and fifty-six bytes of key and two hundred and fifty-six bytes of value.

Multiply it out. Per token, the total K V cache size is sixty-four heads times eighty layers times two hundred and fifty-six bytes times two, for both key and value. That is sixty-four times eighty times five hundred and twelve, which is about two point six megabytes. Per single token. For a sequence of four thousand tokens, the K V cache is about ten gigabytes. For thirty-two thousand tokens, around eighty gigabytes. For one hundred and twenty-eight thousand tokens, over three hundred gigabytes. And this is per request. If you are serving a thousand concurrent users, each with their own conversation context, multiply by a thousand.

This is why inference memory is the real bottleneck, not training. Training uses a lot of memory too, for activations, gradients, and optimizer states. But you can control training memory through batch size, gradient checkpointing, and model parallelism. Inference memory is driven by the product of concurrent users and their sequence lengths, which are set by product requirements, not engineering preferences.

There is another dimension to the inference bottleneck that is worth understanding. Modern G P Us have enormous compute throughput, measured in teraflops, but comparatively limited memory bandwidth, measured in terabytes per second. During autoregressive decoding, each step generates one token. The compute for one token is small, a few matrix multiplies per layer. But the data movement is large, you have to read the entire K V cache and all the model weights from G P U memory for every single token. The ratio of compute to memory access is tiny. The G P U's compute cores sit idle, waiting for data to arrive from memory. This is called being memory-bandwidth-bound. The K V cache makes this worse, because the cache itself is additional data that has to be read at every step.

Now, the question becomes, can we make the K V cache smaller without losing quality?

The first answer came from Noam Shazeer at Google in twenty nineteen, in a paper called Fast Transformer Decoding. The idea is called multi-query attention, or M Q A.

In standard multi-head attention, every head has its own query projection, its own key projection, and its own value projection. Sixty-four heads means sixty-four sets of queries, sixty-four sets of keys, sixty-four sets of values. All sixty-four K V heads contribute to the cache. M Q A keeps all sixty-four query heads but collapses the keys and values down to a single head. One key projection, one value projection, shared across all sixty-four query heads. Each query head still computes its own attention pattern using its own query, but they all attend against the same keys and values.

The K V cache shrinks by a factor of sixty-four. In the example above, from about two point six megabytes per token to about forty kilobytes per token. That is a dramatic saving. For a thirty-two thousand token sequence, the cache drops from eighty gigabytes to about one point three gigabytes.

The catch is quality. Each query head was used to seeing its own dedicated key-value subspace. Now all heads share one key and one value. Think about what this means in terms of the library analogy from episode one. In standard attention, each query head has its own catalog and its own collection of books. In M Q A, all query heads search the same catalog and read from the same books. They can still ask different questions, because they have different queries. But the answers they can find are constrained to what is in the one shared collection.

In practice, M Q A models trained from scratch are nearly as good as full M H A models. Close enough that the inference savings make it worthwhile. But if you take an existing M H A model and try to convert it to M Q A by, say, averaging the K V heads into one, quality drops noticeably. The model needs to be trained with M Q A from the start so it learns to make the most of the shared K V space.

Grouped-query attention, or G Q A, is the middle ground. Proposed by Ainslie and colleagues at Google in twenty twenty three. Instead of one K V head shared by all queries, or sixty-four K V heads matching the queries one-to-one, you use some number in between. Say, eight K V heads for sixty-four query heads. Each K V head is shared by a group of eight query heads. The K V cache shrinks by a factor of eight instead of sixty-four. Quality stays very close to full M H A.

The Ainslie paper had a nice result on converting existing M H A models to G Q A. They showed that you could take a trained M H A model, group the K V heads by averaging within groups, and then do a small amount of additional training to recover most of the quality. This "uptrained" G Q A model was nearly as good as one trained from scratch with G Q A, and much better than the M Q A conversion.

G Q A has become the standard. Llama two uses G Q A in its larger models, with eight K V heads for thirty-two query heads. Llama three uses G Q A across the board. Mistral, Mixtral, DeepSeek, Qwen, Gemma. Nearly every major model released after twenty twenty three uses G Q A with a ratio somewhere between four and eight query heads per K V group.

The intuition for why G Q A works is that key and value representations across heads are more redundant than query representations. Different query heads learn to ask different questions, as we discussed in episode one, the emergent specialization where different heads track syntax, coreference, locality, and so on. But the index and content that keys and values provide have more shared structure. Eight distinct key-value representations are enough for sixty-four query heads to build diverse attention patterns on top of. The queries provide the diversity. The keys and values provide the shared substrate.

There is a nice connection to episode three here. R o P E applies rotations to queries and keys but not values. G Q A shares keys and values across query groups. Together, these define the modern attention head. The query is the individualized, position-aware search signal. One per head. The key is the shared, position-aware index. One per group. The value is the shared, position-free content. One per group. This is not accidental. It reflects the empirical finding that different heads mostly need different questions, not different answers.

Now let me turn to flash attention, which solves a completely different problem. Flash attention does not change the K V cache size. It does not change what attention computes. It does not even change the numerical output, the result matches standard attention up to floating-point reduction order. What it changes is how the computation is organized in hardware memory during the forward and backward pass, primarily during training.

The problem flash attention solves is the memory bottleneck in the attention computation itself. Standard attention materializes the full n-by-n attention score matrix. Here is the sequence of operations. First, compute Q times K transpose, an n-by-n matrix of raw scores. Write this to G P U memory. Second, read it back, apply softmax row-wise. Write the result back. Third, read the softmax output, multiply by V. Write the result. Each of these steps involves reading and writing large matrices to and from G P U high-bandwidth memory, or H B M.

For a sequence of length four thousand, the attention matrix is sixteen million entries per head. For length thirty-two thousand, over a billion. For length one hundred and twenty-eight thousand, over sixteen billion. In sixteen-bit precision, the thirty-two thousand case requires about two gigabytes per head just for the attention matrix. Multiply by the number of heads and layers, and you are looking at hundreds of gigabytes of intermediate memory.

G P U memory has a hierarchy, similar to C P U cache levels. At the top is S R A M, the on-chip memory inside each streaming multiprocessor. It is tiny, typically one hundred to two hundred kilobytes per S M on an A one hundred. But it is extremely fast, with bandwidth measured in tens of terabytes per second. Below that is H B M, the main G P U memory. It is big, forty to eighty gigabytes on an A one hundred, but its bandwidth is about two terabytes per second. The ratio is roughly ten to twenty times in bandwidth.

Standard attention writes the full attention matrix to H B M and reads it back multiple times. The arithmetic operations, the matrix multiplies and the softmax, are fast. The memory round trips are the bottleneck. The computation is memory-bandwidth-bound, not compute-bound.

Flash attention avoids materializing the full attention matrix. It tiles the computation into small blocks that fit entirely in S R A M. For each tile, it computes a block of Q K transpose scores, applies a partial softmax using a numerically stable online algorithm, the online softmax trick by Milakov and Gimelshein, multiplies by the corresponding block of V, and accumulates the result. The key insight is that softmax can be computed in a single pass over the data if you maintain running maximums and running sums. You do not need to see all the scores before normalizing. This means you never need to write the full n-by-n matrix to H B M. You produce the final output block by block, accumulating directly in S R A M.

The result. Memory usage for attention drops from n squared to linear in n. Wall-clock time drops by two to four times on typical sequence lengths, because the H B M round trips are eliminated. And the output is the same attention result, up to normal floating-point differences from the changed reduction order. There is no approximation in the algorithm. It is the same computation, just organized differently in hardware.

Tri Dao published flash attention in twenty twenty two, and flash attention two in twenty twenty three. Flash attention two improved the work partitioning strategy. Instead of parallelizing over batch size and number of heads as in version one, version two also parallelizes over the sequence length dimension, which gives better occupancy on modern G P Us. The result was roughly another two times speedup.

By twenty twenty three, flash attention was integrated into PyTorch's scaled dot product attention function and into every major training framework. You do not even have to think about it anymore. You call the attention function and flash attention runs automatically if your hardware supports it.

One thing to be precise about. Flash attention is primarily a training optimization. During training, you process full sequences, so the n-by-n attention computation happens for the complete sequence. Flash attention makes that computation memory-efficient. During inference, when you are generating one token at a time with a K V cache, the attention computation at each step is a vector-matrix product, one query against all cached keys. That product is already small enough to not need the flash attention treatment. Flash attention does help during the prefill phase, when you process the initial prompt in one shot before starting generation. For long prompts, the prefill can take longer than the entire generation phase, and flash attention speeds it up substantially.

Let me put these three techniques together and explain why they matter as a package.

The deployment cost of a large language model is dominated by two things. Memory for the K V cache, which limits how many concurrent users you can serve on one G P U, or equivalently how long each user's context can be. And memory bandwidth, which limits how fast each generation step runs, because you have to read the K V cache and the model weights for every single token. G Q A attacks the first problem by shrinking the K V cache by a factor of four to eight, directly increasing the number of concurrent users or the maximum context length. Flash attention attacks the compute and memory during the prompt-processing phase. Together, they make it practical to serve models that would have been impossibly expensive just two years earlier.

Before moving on to newer techniques, I want to cover two topics that are as important as G Q A and flash attention for practical deployment but are often discussed separately. Quantization and speculative decoding.

Quantization is about reducing the numerical precision of the model weights and, sometimes, the K V cache. The numbers I quoted earlier assumed sixteen-bit precision. But production serving almost universally uses lower precision. Eight-bit integer quantization, I N T eight, cuts the memory footprint in half with minimal quality loss. Four-bit quantization, I N T four, cuts it by another factor of two. A seventy billion parameter model that requires one hundred and forty gigabytes in sixteen-bit precision fits in about thirty-five gigabytes at four-bit precision, which means it can run on a single high-end consumer G P U instead of requiring multiple data center G P Us.

The challenge is that naive quantization, just rounding weights to fewer bits, introduces significant error. Modern quantization methods are much smarter. G P T Q, published in twenty twenty two, uses approximate second-order information to minimize the quantization error layer by layer. A W Q, Activation-aware Weight Quantization, from twenty twenty three, observes that a small fraction of weight channels are much more important than others, because they correspond to large activation magnitudes, and protects those channels while aggressively quantizing the rest. Both methods can quantize a model to four bits with less than one percent degradation on most benchmarks.

The K V cache can also be quantized. Since the cache dominates inference memory for long sequences, quantizing cached keys and values from sixteen bits to eight or even four bits gives another two to four times memory reduction. The quality impact is slightly larger than weight quantization, because the cache is accessed at every step and errors accumulate, but for most applications the tradeoff is worthwhile.

Speculative decoding is a different kind of optimization. It does not reduce memory. It reduces latency by addressing the fundamental bottleneck of autoregressive generation, which is that you generate one token at a time, each requiring a full forward pass through the model.

The idea is to use a small, fast draft model to generate several candidate tokens cheaply, and then verify all of them in a single forward pass of the large target model. The draft model might be a two billion parameter model, running at ten times the speed of the seventy billion parameter target. It generates, say, five candidate tokens in the time the target model would generate one. Then you feed all five candidates to the target model in a single forward pass, computing the target model's probability distribution at each position. If the target model agrees with the draft model's choices, all five tokens are accepted and you have generated five tokens in the time it would normally take to generate two. If the target model disagrees at position three, you accept the first two tokens, reject the rest, and sample a corrected token from the target model's distribution at position three.

The key property is that the output distribution is mathematically identical to what the target model would have produced on its own. There is no quality loss. The draft model only proposes. The target model decides. The speedup depends on the acceptance rate, which depends on how well the draft model matches the target. In practice, a well-matched draft model gives acceptance rates of seventy to eighty-five percent, translating to two to three times generation speedup.

Some models are designed with speculative decoding in mind. Medusa adds multiple prediction heads to the model itself, so it can propose several future tokens in a single forward pass without needing a separate draft model. Eagle, from twenty twenty four, uses a lightweight layer that predicts multiple steps ahead based on the model's hidden states. These approaches avoid the need to maintain a separate draft model while preserving the verify-then-accept framework.

Now let me mention two more techniques that extend the K V cache ideas.

Paged attention, from the v L L M project, released in twenty twenty three. In a serving system, different requests have different context lengths. One user has a five-hundred-token conversation. Another has twenty thousand tokens. If you pre-allocate K V cache memory for the maximum possible length for every request, you waste enormous amounts of memory on the short requests. Paged attention borrows the virtual memory concept from operating systems. The K V cache is divided into fixed-size pages, typically sixteen or thirty-two tokens per page. Pages are allocated on demand and can be non-contiguous in physical G P U memory. A page table maps logical token positions to physical memory locations. This dramatically improves memory utilization in real serving workloads where request lengths vary.

Multi-head latent attention, from the DeepSeek team. Instead of caching the full key and value vectors, project them into a lower-dimensional latent space before caching. The cached representation is much smaller. At each decoding step, you project the latent representation back up to the full dimension before computing attention. This adds a small computation cost but can reduce the cache size by another factor of two to four beyond G Q A.

The broader lesson here is about where the field's engineering effort goes. The transformer architecture has not changed much since twenty seventeen. The core computation, query-key-value attention with residual connections and feed-forward networks, is the same. What changed is the systems engineering. R o P E, G Q A, flash attention, paged attention, better normalization, better initialization. These are not new architectures. They are refinements that make the same architecture practical at scales and costs that were impossible in twenty seventeen.

This is a pattern worth naming. In the early days of a new architecture, the gains come from architectural innovation. In the mature phase, the gains come from systems engineering. Transformers entered the mature phase somewhere around twenty twenty two. The architecture was settled. The race became about who could serve it most efficiently.

Replace the single M L P in each layer with multiple parallel M L Ps, and only activate a subset per token. This decouples model size from inference cost, and it is the architecture behind the frontier models of twenty twenty four and twenty twenty five.
