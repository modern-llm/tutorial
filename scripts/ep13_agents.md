# Episode 13: Agents, from prompts to systems

Welcome to episode thirteen. For most of this series we have been inside the model. Architecture, training, post-training, reasoning. Today we step outside. We are going to talk about what happens when you put a language model inside a loop, give it tools, and let it take actions in the world. This is the agent paradigm. And the most important thing I can tell you upfront is that the gap between "agent" as a concept and "agent" as a reliable production system is larger than most people expect.

Let me start with the minimal agent loop, because everything else is built on top of it. You have a language model. You have a set of tools. A web search function. A code executor. A file reader. A calculator. A database query interface. You give the model a task as a natural-language prompt. The model generates a response that includes a structured tool call, specifying which tool to use and with what arguments. Your runtime, which is ordinary software, intercepts the tool call, executes it, and appends the result back to the model's context. The model sees the result and decides what to do next. Maybe another tool call. Maybe a final answer. The loop continues until the model indicates it is done, or you hit a maximum iteration limit.

That is it. That is the complete agent architecture. Model emits action. Runtime executes action. Result appended to context. Model emits next action. Repeat. Everything else in the agent literature is engineering around this loop's failure modes.

This pattern was formalized in the ReAct paper from twenty twenty two, by Yao, Zhao, and colleagues at Princeton. ReAct stands for Reasoning plus Acting. The model alternates between reasoning steps, where it writes out its thinking as plain text, and action steps, where it produces a structured tool call. The reasoning steps let the model plan, interpret results, and decide what to do next. The action steps let it interact with external systems. By interleaving reasoning and acting, the model can handle multi-step tasks that require gathering information, computing results, and synthesizing answers.

ReAct was a conceptual milestone, but the original implementation was rough. The model generated tool calls as free-form text embedded in its output, and the runtime had to parse them out with string matching or regular expressions. If the model formatted the tool call slightly wrong, parsing failed and the step was wasted. This was the state of the art in twenty twenty two and early twenty twenty three.

By late twenty twenty three, the major A P I providers, OpenAI, Anthropic, Google, standardized tool calling as a first-class feature of their A P Is. Instead of the model producing tool calls as text that you parse, you define your tools as structured schemas, J S O N schema descriptions of function names, parameter types, and descriptions. The model produces a structured tool-call object with the function name and typed arguments. The A P I returns this as structured data, not as text you have to parse. You execute the tool, send the result back as a structured tool-result message, and the model continues.

This sounds like a small improvement, but it was transformative for reliability. Parsing errors dropped to near zero. Argument type mismatches became catchable at the schema level. Models were fine-tuned specifically to produce well-formed tool calls, not just to write text that looks like tool calls. The shift from string-parsing ReAct to structured tool calling is analogous to the shift from string-based R P C to typed R P C in traditional software engineering. The same pattern, but with guardrails that eliminate an entire class of errors.

The basic loop, though, is unchanged. Generate. If a tool call is present, execute it. Append the result. Generate again. If a final answer, return it. If the iteration cap is hit, return whatever you have.

So why has the agent paradigm attracted so much attention? Because when this loop works, it is extraordinarily powerful. A model that can search the web, read documents, write and execute code, and iterate on its results can solve tasks that no single prompt-response interaction can handle. Multi-step research questions. Code debugging that requires reading error messages, editing code, and re-running tests. Data analysis that requires querying a database, transforming the results, generating a visualization, and interpreting the chart. These are tasks where the number and type of steps cannot be predicted in advance, so you cannot hard-code a pipeline. You need the model to decide the path dynamically.

And when the loop fails, it fails in ways that are educational and important to understand. Let me go through the major failure modes systematically, because understanding these is more valuable than understanding any particular agent framework.

Hallucinated tool arguments. The model calls a function with arguments it fabricated. It searches for a U R L that does not exist. It calls a function with the wrong number of arguments. It uses a parameter name from a different tool's schema. It references a file path it saw in a different context that does not exist here. The root cause is that the model is generating tool calls as text, and it can generate any text, including text that looks like a valid tool call but is not. The mitigation is strict schema validation on every tool call, rejecting invalid calls and returning a clear error message to the model, giving it a chance to self-correct.

Infinite loops. The model gets stuck repeating the same action. It searches for the same query, gets the same result, decides the result is insufficient, searches again with the same query. Or it edits a file, runs a test, gets an error, makes the same edit, runs the test again, gets the same error. The model has enough context to realize it is looping, but it does not. This happens because L L Ms do not have strong metacognition about their own behavior across turns. The mitigations are a hard iteration cap and a repetition detector that compares recent actions to previous actions and breaks the loop with an explicit prompt about what went wrong.

Premature stopping. The model declares it is done before it has actually solved the problem. This is especially common when the model can generate a plausible-sounding answer from its parametric knowledge alone. It might give a direct answer to a factual question without bothering to verify through a search. Or it might write code that looks correct at a glance but has a bug it could have caught by running the tests. The fix is task-specific validation on the final answer. Did the code pass the tests? Does the answer cite a source? Is the answer consistent with the information gathered during the session?

Context blowout. Each tool call adds its result to the message history. A web search might return two thousand tokens of snippets. A code execution might produce a long traceback. After ten or twenty tool calls, the conversation history is tens of thousands of tokens of accumulated results, most of which are no longer relevant to the current step. The model has to attend to all of this, and it starts losing track of its original goal. Important details from early in the session get diluted by irrelevant details from later steps.

The mitigations are summarization checkpoints, where you periodically ask the model to distill the conversation so far into a compact summary and replace the raw history with the summary, and state externalization, where you write critical intermediate results to files or structured notes rather than relying on the message history to carry them.

Lost state across turns. Related to context blowout. If the model's working memory is entirely in the message history, and that history gets summarized or truncated, critical information can disappear. A key finding from step three might get dropped during a summarization at step eight, and the model spends steps nine through twelve re-deriving it. The mitigation is to externalize important state proactively. When the model discovers something important, it should write it to a file or scratchpad, not just leave it in the conversation.

These failure modes are not bugs in any particular framework. They are structural properties of the architecture. Any system that gives an L L M autonomous decision-making over an unbounded number of steps, with tool results of variable quality and length, will exhibit these behaviors. The engineering challenge is making them rare enough and recoverable enough that the system delivers net value.

Now let me describe the design patterns people use, ordered from simplest to most complex. The most important principle, articulated clearly in Anthropic's Building Effective Agents essay, is start with the simplest pattern that works. Add complexity only when the simpler pattern fails.

Pattern one. Workflows. Also called chained prompts or orchestrated pipelines. A fixed sequence of L L M calls, with no autonomy or branching. Step one, extract key facts from the document. Step two, summarize those facts. Step three, translate the summary. Each step is a single L L M call with a specific prompt. The output of one step feeds as input to the next. There are no tool calls, no loops, no decisions. The topology is fixed at design time.

This is not an agent. It is a pipeline. But here is the important point. Most production A I features are this. And that is the right choice. A pipeline is deterministic in its structure, predictable in its cost and latency, easy to test, easy to debug, and easy to monitor in production. If your task can be decomposed into a fixed sequence of L L M operations, do that. Do not add autonomy you do not need.

Pattern two. Routing. A classifier L L M looks at the input and decides which of N downstream handlers to invoke. "Is this a billing question, a technical question, or a general question?" Route to the billing handler, the tech handler, or the general handler. Each handler can be a simple prompt, a workflow, or even a specialized model. The routing decision is the only L L M judgment call. Everything downstream is deterministic.

Routing is useful when you have inputs from many different categories, each requiring different treatment. It lets you use specialized prompts and models for each category instead of stuffing everything into one mega-prompt and hoping for the best.

Pattern three. Parallelization. Run multiple L L M calls concurrently on different aspects of the input, then aggregate. Evaluate an essay on grammar, logic, and style simultaneously with three different prompts. Generate five candidate answers and vote. Analyze a document from three different perspectives and synthesize. The key feature is independence. Each parallel call works on the same input but from a different angle, and the results are combined by a simple aggregation step, voting, concatenation, or a final synthesis prompt.

This is useful when a single prompt cannot capture all the dimensions you need, and the dimensions are independent enough to process in parallel.

Pattern four. The tool-use loop. This is the actual ReAct agent. The model receives a task, decides which tool to call, examines the result, and decides whether to call another tool or produce a final answer. The loop continues until the model declares it is done or the iteration cap is hit. This is needed when the steps are not predictable in advance. Question answering that requires multiple searches and cross-referencing. Code debugging that requires reading, editing, and testing in an unpredictable sequence. Research tasks where what you learn in step two determines what you should do in step three.

Pattern five. Planner plus executor. Split the agent into two phases. First, a planning phase where the L L M produces a numbered plan, a specific sequence of steps to accomplish the task. Second, an execution phase where a separate loop, possibly a simpler L L M, executes each step in order, potentially using tools.

The advantage is structure. The plan provides guardrails for the execution, making it less likely to wander off track. The disadvantage is rigidity. Plans become stale as the world changes. If step three reveals that the premise of step five is wrong, the executor either follows a bad plan or has to trigger replanning, which is expensive and resets context. In practice, the planner-executor pattern works well for tasks where the steps are mostly predictable and the risk of stale plans is low, like code generation from a spec.

Pattern six. Reflection. After the agent produces its output, a separate L L M call evaluates it. "Is this response correct? Does it address the original question? Are there errors or missing pieces?" If the critic finds issues, the agent retries. This catches obvious errors and is especially valuable when the cost of a wrong answer is high. The downside is that it doubles the cost and latency per iteration, and the critic itself can miss errors or flag correct responses as wrong.

Pattern seven. Multi-agent systems. Multiple specialized agents, each with their own tools, system prompts, and possibly different models, coordinated by an orchestrator agent. A researcher agent searches the web. A coder agent writes code. A reviewer agent checks the code. The orchestrator decides which agent to invoke, passes information between them, and assembles the final result.

This sounds appealing because it mirrors how human teams work. But in practice, multi-agent systems introduce coordination overhead that usually outweighs the specialization benefits. Each handoff between agents is a potential failure point. Context gets lost or mangled during transfer. The orchestrator needs to make meta-level judgments about what to delegate and when, and it is prone to the same failures as a single agent, hallucinated delegations, infinite delegation loops, premature resolution, but now with added complexity.

Anthropic's recommendation, echoed by most teams with production experience, is clear. Do not reach for multi-agent systems unless coordination is genuinely the bottleneck. A single agent with good tools, clear instructions, and appropriate context almost always beats a multi-agent system on cost, latency, reliability, and debuggability. Multi-agent is warranted when you need genuinely different models, like a vision model and a code model, or when the subtasks are so different that a single system prompt cannot cover them. That bar is higher than most people think.

Let me connect this to the broader series. In episode twelve we talked about reasoning models that improve by thinking longer. An agent is reasoning plus acting. The thinking is interleaved with tool use. And the same test-time compute principle applies. More agent iterations means more compute, potentially better results, but with diminishing returns and increasing risk of failure. The practical tradeoff is the same. Easy tasks should use simple patterns with few iterations. Hard tasks justify more complex patterns with more iterations. Match the system complexity to the task complexity.

There is also a relationship between model capability and agent reliability that is worth stating explicitly. Weaker models fail more often as agents. They hallucinate tool arguments more frequently. They lose track of state faster. They loop more. They stop prematurely more. Stronger models, especially models specifically trained for tool use and multi-step reasoning, are dramatically more reliable agents. A large fraction of the improvement in agent performance between twenty twenty three and twenty twenty five came not from better frameworks or patterns but from better underlying models. The same ReAct loop works much better when the model inside it is stronger. If your agent is unreliable, upgrading the model is almost always more effective than adding framework complexity.

The practical hierarchy, one more time. First, try a single prompt. If that is not enough, try a workflow. If the steps are unpredictable, use a tool-use loop. Add a planner if the task is long. Add a critic if mistakes are costly. Reach for multi-agent only when you have genuinely independent subtasks requiring different specializations. At each step up, the system becomes more capable but also more fragile and expensive. Match the complexity to the task.
